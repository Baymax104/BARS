# IntRR 训练耗时排查

## 结论

2026-10-20北京时间01:10–01:16的被动观测表明，当前速度下降的主要证据指向 **GPU共享竞争**，双卡DDP会等待较慢的一侧；每100步一次的完整验证又扩大了整体耗时。当前仍为1格训练、7格串行排队。首格Beauty200／`swu5s4wy`正常推进，未见配置漂移或停止更新。

本轮仅读取已有W&B历史、进程与GPU计数器、运行源码归档；新增训练、Testing与模型forward均为0，没有修改或重启正式训练。此为诊断完成记录，尚未应用或量测提速改动。

交接复核：北京时间2026-10-20 **01:21:44**，`swu5s4wy`仍为running，日志已到实际 **44,400／50,000步**；其余七格均为`waiting_predecessor`。训练仍持续推进，后文耗时统计绑定此前采样窗口。

## 对照与计时方法

参照为已完成的Beauty42训练[oipt22mb](https://wandb.ai/baymaxam/GRID/runs/oipt22mb)，当前为Beauty200训练[swu5s4wy](https://wandb.ai/baymaxam/GRID/runs/swu5s4wy)。两者实际W&B中的model、data及trainer配置（剔除输出目录）一致；50k、FP32、global batch256、Adam、每100步验证和beam10等不变。训练seed分别为42和200，属于性能对照，不解释为推荐质量的匹配重复。

计时来自完整W&B历史的`_timestamp`：`train49→train99`等相邻事件表示50步纯训练区间；同一optimizer step的train事件至val事件表示验证区间；相邻val事件表示100步训练加一次验证的周期。保留事件末尾日志开销，属于阶段墙钟计时，不是CUDA kernel profiler。日志`trainer/global_step`加1对应实际optimizer step。

旧run有1500条事件、500次验证；本轮截取当前1265条事件、421次验证，最后训练日志对应42,200步。完整历史、分段统计及资源样本见[证据目录](evidence/intrr-speed-diagnosis-20261020/README.md)。

## 同一进度区间的实测耗时

以下均为中位数，单位秒。

| 区间／阶段 | 旧Beauty42 | 当前Beauty200 | 当前／旧 |
|---|---:|---:|---:|
| 1–20k：50步纯训练 | 2.546 | 2.637 | 1.04× |
| 1–20k：一次验证 | 7.680 | 7.718 | 1.00× |
| 1–20k：100步完整周期 | 12.983 | 13.115 | 1.01× |
| 25k–40k：50步纯训练 | 1.856 | 5.355 | 2.89× |
| 25k–40k：一次验证 | 4.513 | 19.219 | 4.26× |
| 25k–40k：100步完整周期 | 8.234 | 30.141 | 3.66× |
| 40k–42.1k：100步完整周期 | 8.196 | 15.351 | 1.87× |

同一实现前20k速度基本重合，之后训练和验证同时变慢，并有明显波动。整段已记录事件中，当前完整周期平均20.116秒，旧run平均10.458秒；因覆盖进度不同，该整体均值仅作概览，同进度窗口是主要比较依据。

当前已记录墙钟时间约62.6%落在验证区间，旧run约57.6%。每100步一次全量beam验证是当前冻结的TIGER对齐协议；减少验证次数会改变选点机会，本轮保持该配置。

## GPU与系统证据

实际IntRR rank0／rank1为PID3201187／3201188，位于物理GPU0／7，UID1046。01:15的`/proc`与NVML交叉核准，GPU0和GPU7还各有两个UID1051的其他用户进程；进程会持续替换，不能只等待某个固定PID退出。

进程级`nvidia-smi pmon`五次采样中，GPU7上IntRR rank1的SM活动为24／22／9／19／16%，同卡另一个任务为61／65／69／39／82%。更早一次样本则显示GPU0上的其他任务占用更高。它们是短窗口活动计数，包含通信活动，不能直接换算为独占训练加速比；但确认了运行期间的跨用户GPU竞争，且瓶颈侧随外部负载变化。

01:10 CPU load约69（192核），可用内存约508GiB，未见系统级CPU或RAM耗尽。数据加载未做单独模型重放或CUDA profile，不能给出其独立耗时；现有证据已足以优先处理GPU竞争。

原队列guard在每格启动前核对其他用户占用，`flock`只约束我方队列。它不能保留或隔离GPU，也不能阻止其他用户在训练开始后使用同卡。启动时资源核验通过与当前出现混用并不矛盾。GPU3／4／5仍为root常驻服务，当前没有可直接替换的空闲双卡。

## 实现检查

两次真实运行源码快照中的16份IntRR模型、数据适配、入口、TIGER训练协议及预处理文件逐SHA256一致；结果见`source-comparison.json`。当前生成路径使用张量化前缀检索和topk，没有在beam候选循环中逐候选调用`.tolist()`，未发现旧LETTER那类逐候选CPU回传模式。该检查不替代CUDA同步次数profile。

明确存在的一处冗余是：`src/recommendation/intrr/module.py:204`的`eval_step`先调用`losses`，后调用`generate`；两者分别在第152／176行调用`encode_history`，因此每个validation batch会完整执行两次历史RAN和T5编码，第二次alignment loss也被丢弃。它在旧run中同样存在。本轮未量测复用编码状态的提速幅度，因此不将其解释为本次阶段性变慢的独立原因，也不承诺加速倍数。

## 处理顺序与当前动作

优先获得稳定的双GPU计算资源，再评估实现优化。当前正式run继续按原50k／500次验证更新；没有杀进程、迁移设备、更改batch／精度／验证频率，七格队列及原预算保持。后继仍按guard核准资源后启动，其他用户持续占卡时会等待。

代码优化的最小候选是仅在eval路径复用同一次历史编码，再比较固定checkpoint下的loss、候选SID、分数及Top10等价性，并量测验证耗时；训练计算与选点频率保持。该候选尚未实施，本次没有新增实验预算或在共享GPU上追加benchmark负载。

## 可复核命令

从GRID根目录重放保存的真实历史并检查近期周期是否超过旧run的1.5倍：

```powershell
uv run --no-sync python docs/evidence/intrr-speed-diagnosis-20261020/collect_timing.py --from-cache --assert-no-regression
```

本次实际输出`last20_cycle_ratio=1.850996192618653`、`slowdown_alert=true`，按设计退出1；这是针对已观察慢速的告警，不是模型正确性单元测试失败。该脚本不实例化模型，缓存重放不读取外部服务；去掉`--from-cache`时仅对指定两个W&B run刷新历史。
